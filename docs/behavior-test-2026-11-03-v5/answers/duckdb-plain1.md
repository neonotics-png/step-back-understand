# DuckDB 2.0 / Quack quiz answers

1. **Server vs client.** The server is an ordinary DuckDB process that owns the database file and runs `CALL quack_serve(...)` (or `duckdb -serve`). Clients are other DuckDB processes (CLI, apps, even DuckDB-Wasm) that `ATTACH 'quack:host' AS x (TOKEN ...)`. If you only attach, the remote shows up as another catalog: you query it with qualified names (`x.table`), and writes, DDL and BEGIN/COMMIT are forwarded to the server while the rest of your session stays local. `CONNECT x` switches the whole session to the remote, so every statement after it runs on the server and results stream back until you `DISCONNECT`. There is also a stateless `quack_query(uri, sql)` for one-off queries.

2. **Wire protocol.** Quack runs over plain HTTP or HTTPS, on port 9494 by default. The client always starts each exchange and the server never pushes. Messages use DuckDB's own binary serialization, sent as the MIME type `application/duckdb`. It is the same serialization DuckDB uses for its WAL, so complex types arrive without loss. Once connected, a query usually needs a single request/response round trip. Large results come back in chunks through follow-up FETCH requests, which can run in parallel.

3. **Default protection.** Out of the box the server binds only to localhost (other addresses need `allow_other_hostname = true`). It also requires a token on every connection and generates a random one if you don't set your own. Non-local connections default to HTTPS, but with a self-signed certificate. What it doesn't protect against: anyone holding the token gets the full SQL surface, reads and writes alike, because the default authorization (`quack_nop_authorization`) allows everything. Localhost traffic is also unencrypted. Authentication runs once at connect time and checks who the caller is (default `quack_check_token` compares tokens). Authorization runs before each query and decides whether it may run; it can reject the query or return replacement SQL. Operators swap either one by setting `quack_authentication_function` / `quack_authorization_function` to their own function. That can be a SQL macro, or an extension for stateful policies. Callbacks run on a fresh connection with no session state.

4. **Why HTTP and a custom format.** HTTP comes with mature tooling for load balancers, proxies, firewalls, auth and intrusion detection, and it lets DuckDB-Wasm in a browser connect natively. They passed on Arrow Flight SQL because they didn't want to depend on formats someone else controls, and because Flight SQL needs two round trips per query where they wanted one. Their benchmark also showed Flight much slower (17.4 s vs 4.9 s bulk transfer, and roughly half PostgreSQL's small-insert rate). For PostgreSQL's wire protocol, my sources didn't give an explicit reason. What they did show: Postgres clients can't parallelize result reads, Postgres took 158 s on the bulk transfer, and a foreign protocol can't carry DuckDB's types without loss the way its native serialization can.

5. **Why a server process.** DuckDB keeps much of a database's state in memory inside the process. Several independent processes writing one file would each have to keep that in-memory state in sync, which is hard and slow. A single server process avoids that problem. It fits the existing engine because DuckDB already has MVCC and optimistic concurrency for many writer threads in one process. Quack funnels writes from many processes into that one process, so the existing machinery handles them unchanged, and it reuses the existing WAL serialization on the wire.

6. **Before Quack, and alternatives.** Before Quack, one process could open a file read-write, or several processes could open it read-only, but there were no multi-process writers. Workarounds were custom RPC/API services wrapping DuckDB, Arrow Flight SQL wrappers, and PostgreSQL-based setups. DuckLake is different: it is a lakehouse format where data lives in object storage and the catalog in a database such as PostgreSQL, so many independent DuckDB instances read and write without a DuckDB server. Quack is a live client-server connection to one DuckDB instance, and it may later serve DuckLake catalogs. MotherDuck: I didn't research it this session. From general knowledge, it is a commercial managed cloud DuckDB service with hybrid local/cloud execution, while Quack is a free, self-hosted open protocol.

7. **Reception.** I didn't find much on how practitioners received Quack itself, so I can't say much without guessing. What I saw: news coverage framed it as DuckDB "adding a server to a database built to run without one", and the official blog stressed that it replaces ad-hoc workarounds. Enthusiasm plausibly comes from that and from the strong benchmarks. Skepticism I did see was about stability: 1.5.x called it a preview subject to change, and coverage called its graduation from beta the release's big test. The related AWS acquisition of DuckLabs drew criticism from MotherDuck's CEO, but that was about AWS, not Quack.

8. **Sensor-ingestion scenario.** Make one process the Quack server that owns the file. Either the ingestion service calls `quack_serve` itself, or a dedicated serving DuckDB runs and ingestion connects to it as a client. The dashboard connects over `quack:localhost`, and the analysts `ATTACH` remotely and `CONNECT`. Their UPDATEs are forwarded to the server and run under its MVCC, alongside ingestion. If two analysts correct the same reading at once, optimistic concurrency control applies: one commits and the other's transaction fails with a conflict error and has to be retried. It is not silently merged. Before exposing it: keep Quack bound to localhost and put a TLS-terminating reverse proxy (nginx/Caddy) with a real certificate in front, rather than using `allow_other_hostname` (described as only for testing) with a self-signed cert. Set strong tokens, ideally per analyst through `quack` secrets, and replace the allow-everything authorization with real rules, for example limiting what analysts can modify. Optionally add network limits such as firewall rules or a VPN.
