# DuckDB 2.0 / Quack quiz answers

**1. Server, client and CONNECT vs ATTACH.**
The server is an ordinary DuckDB process that owns the database file and calls `quack_serve(...)` (or runs `duckdb -serve`). It listens on port 9494 by default. A client is also an ordinary DuckDB, with the auto-loaded `quack` extension, so each client is a full engine of its own. `ATTACH 'quack:host' AS qk (TOKEN ...)` adds the remote database as one more catalog. You name its tables as `qk.table`, and you can join them with local tables while the local database stays the default. `CONNECT qk` switches the whole session to the server: every later statement runs there and results stream back, until `DISCONNECT`. Transactions (`BEGIN … COMMIT`) are forwarded to the server. `CONNECT` also works against PostgreSQL and MySQL, with remote pushdown.

**2. Transport and wire format.**
Quack runs over plain HTTP, with HTTPS for non-local hosts in 2.0. It is strictly request/response, and the client starts every exchange; the server never initiates one. Data is sent as DuckDB's own internal vector blocks, using the serializer DuckDB already uses for its write-ahead log (MIME type `application/duckdb`), so neither side converts anything. On an open connection a typical query completes in one round trip. Large results are fetched with follow-up fetch requests, which can run in parallel across threads.

**3. Access control.**
By default the server binds only to localhost; another host requires `allow_other_hostname = true`. It also requires a shared token, which is randomly generated if you don't set one. There are no built-in users, and the default authorization allows every query. TLS is off on localhost, and non-local servers use only a self-signed certificate, so it does not give real per-user control or internet-grade transport security. The authentication hook (`quack_authentication_function`, default `quack_check_token`) runs when a connection is requested. It decides whether a client may connect at all. The authorization hook (`quack_authorization_function`, default a no-op) runs on each prepared query, and it can reject the query or rewrite it. Operators replace either hook with a SQL macro, for example one that looks tokens up in a table, or with an extension UDF. Read-only rules should check the statement type or use a read-only attach, not match on the query text.

**4. Why HTTP with its own format.**
The team picked HTTP because in 2026 it comes with load balancers, proxies, firewall rules and auth tooling. It also lets DuckDB-Wasm in a browser speak Quack directly. They rejected the PostgreSQL wire protocol because it is row-oriented and its standard clients don't read in parallel: in their benchmark, 60M rows took about 158 s over Postgres against about 5 s over Quack. They rejected Arrow Flight SQL for two reasons. Every query needs at least two round trips (`CommandStatementQuery` then `DoGet`). And the format is controlled by others, which would stop DuckDB from adding types or messages on its own schedule. Their own format reuses existing internals and needs no conversion.

**5. Why a server process.**
An in-process engine keeps a lot of state in memory: caches and transaction bookkeeping. Several processes writing one file would have to keep that memory in sync with each other, which is complex and slow. That is why DuckDB locks the file for a single read-write process. Within one process, DuckDB already had multi-connection MVCC (adapted from HyPer) with optimistic concurrency control. Putting one server process in front of the file reuses all of that unchanged: remote clients simply become more connections to the same transaction manager. So server mode could ship as an extension rather than a storage rewrite.

**6. Before Quack, and how it compares.**
Before Quack, one process could open a file read-write, or many processes could open it read-only, never both. People worked around this with custom RPC or HTTP services, wrappers built on Arrow Flight SQL, MotherDuck (with its own protocol), and pg_duckdb inside PostgreSQL. Quack gives you a self-hosted single server with many writers. DuckLake gets multiple writers a different way: many DuckDB instances share Parquet files in object storage through a central catalog, which scales out but is less simple. A Quack server can now act as that catalog. MotherDuck is the managed service. It adds real users and SSO, separate storage and compute, read scaling, scale-to-zero, time travel, zero-copy clones and an SLA, none of which Quack provides. Quack is tied to one instance and has no replication yet.

**7. Reception.**
Reception was mostly positive. Hacker News was largely favorable, a Reddit user called it "a big unlock," and third-party clients appeared within weeks, including Columnar's ADBC driver in preview. MotherDuck publicly welcomed it and plans to accept Quack connections. The enthusiasm came from a long-standing pain point, the single-writer lock, now solved officially with minimal setup and strong bulk-transfer performance. The skepticism: it is still one node with no replication or failover, and you run and secure it yourself. Its security defaults are minimal. Its write throughput tops out at a few thousand transactions per second, with Postgres scaling better past 8 threads, so it is not an OLTP replacement for Postgres. I didn't find detailed critical threads, so I can't speak to the specific critiques.

**8. The sensor-ingestion scenario.**
Make the ingestion service the Quack server, or have it connect to one: a single DuckDB process on the VM owns the file and runs `quack_serve` with an explicit strong token. Ingestion, the dashboard and the analysts all go through it as clients. While the server holds the file, nothing else can open the file directly, not even read-only. Appends from ingestion won't conflict with anything. If two analysts update the same reading at the same time, I expect the second to commit to fail with a "Transaction conflict" error, which they must retry, rather than waiting on a lock as Postgres would. That is DuckDB's documented optimistic behavior; the Quack docs don't spell it out, so test it. Before exposing it:
- Keep Quack bound to localhost and put an nginx or Caddy reverse proxy in front that terminates TLS with a real certificate, rather than setting `allow_other_hostname` and exposing it directly.
- Replace the default auth hook with per-analyst tokens kept in a table.
- Optionally use an authorization hook that checks statement types, limiting analysts to `SELECT` plus `UPDATE` on the readings table.
- Add firewalling.
