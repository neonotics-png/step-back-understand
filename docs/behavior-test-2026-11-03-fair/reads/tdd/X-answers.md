# TDD quiz answers

1. The red bar tells you what to do next. Red means "now write just enough code", and the rule says new code is only allowed once a test has failed, so the failure is your permission to write code. The test is a runnable statement of the expected answer, like the hand-typed output tape. If it passes the first time, you never saw it catch the missing behaviour: either the behaviour already exists or the test isn't checking what you meant. Either way you have no evidence the test can tell right from wrong. (The explainer doesn't say this outright; the "test that can't fail" point is my reasoning from the red-as-signal idea.)

2. Sins are acceptable because the refactor step always comes next, and the passing tests make it safe to clean up. The two steps depend on each other. A faked constant is also useful: the duplication between the test's expected value and the hard-coded constant is the signal that drives generalization in the refactor step (Fake It, then Triangulate). If you try to write the clean final design while getting to green, you merge "make it run" with "make it right". Canon TDD lists that as a mistake. Your steps get bigger, you stay red longer, and you make implementation design decisions before you have a passing test to protect them.

3. The refactor step removes duplication. That means the duplication created just to get the test to work, including the duplication between the test and the code, and it is where implementation design decisions get made. It needs no new failing test because it only reshapes code that already works: it happens only on green, and the existing tests protect it. Beck's loop has no up-front design phase, so after a long run of red-green with no refactoring you get a pile of uncleaned "sins": hard-coded constants, copied code, never-generalized special cases and no deliberate implementation design. (Fowler's specific claim that this is the most common mistake is not in the explainer.)

4. Writing every test before any code is the old tape-era form: one big expected output for the whole program, made once. Beck deliberately broke that into small pieces, and Canon TDD lists "convert all the items on the Test List into concrete tests, then make them pass one at a time" as a mistake. What you write up front is a test list, a behavioural analysis of what you are and aren't building. During the loop you turn exactly one item into a runnable test, make it and all earlier tests pass, optionally refactor, then pick the next item. Doing one at a time ("just do one") keeps steps small and gives a single clear red signal. Each test's interface decisions can then build on what you learned from the previous one.

5. You pick a gear by how confident you feel. When you're unsure, use Fake It (return a constant) or Triangulate (generalize only once you have two or more examples). When the answer is clear, use Obvious Implementation and type in the real code. Beck links this to fear: tests let you "choose your level of fear". So "TDD means tiny steps" is too simple. Tiny steps are one setting you can choose, and step size is a judgment call, not a fixed rule.

6. Writing the test first forces interface decisions: what the code is called, what it takes and returns, and what answer you expect. That matches the wiki's "the interface & output of an object are more important than its implementation, so write the former first". Implementation design decisions, meaning how the code works inside and how it is structured, wait for the refactor step on green. The split works because each kind of decision is made when you have the right information and protection. You state what you want before writing code, and you clean up how it works only once the tests pass and can catch mistakes, with no big up-front design phase.

7. In Beck's loop the test is a specification of behaviour, and refactoring changes only the implementation while staying green. Tests that break whenever the implementation changes, even though behaviour hasn't, make the refactor step unsafe and expensive. That removes the protection that makes green-step "sins" acceptable. Asserting values pasted from the code's own output turns the tape idea upside down: the expected answer is meant to be decided first, independently, so a test that copies the code's output can't tell you the code is wrong. Their tests should state expected behaviour through the interface, with expected values chosen in advance, and stay stable when internals are reshaped. (The explainer doesn't discuss mocking; the point about mocks coupling tests to implementation is my reasoning from the interface/implementation split.)

8. Beck would say test-first "is not testing". It is an analysis technique (deciding what you are and aren't building and what answers you expect) and a design technique, with the goal of "clean code that works". Coverage is a side effect, and Canon TDD even calls tests written "without assertions just to get code coverage" a mistake. On how much to use it, Beck ties step size to fear and confidence ("choose your level of fear"): you take smaller steps when unsure and use Obvious Implementation when confident, rather than following a fixed every-line ritual. (The explainer doesn't say when Beck would skip TDD entirely; that part of the answer is not covered.)
