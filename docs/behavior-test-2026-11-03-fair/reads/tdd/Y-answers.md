# TDD Quiz Answers

1. Watching the new test fail proves it can fail at all. A test that passes before you write anything is testing nothing, or the feature already exists. It also lets you check that it fails for the reason you expect: "expected 10 but got 0" is the right red, while something like a NullPointerException in setup tells you something else is wrong. If it passed the first time, you would lose that small red-then-green experiment that confirms both the test and the code, so you couldn't trust that the test checks anything.

2. While you're red you have no safety net, and while you're green you do, so the only goal of green is to get back to passing as fast as possible. Fake It lets you take the smallest possible step, and a hard-coded constant isn't wasted work: the refactor step removes the duplication between test and code (the 10 in the test and the 10 in the code are really 5 * 2), and that is what turns the fake into a general implementation. Trying to write the clean final design while getting to green mixes two goals ("works" and "clean"), which TDD deliberately splits. That means bigger steps, a longer gap between decision and feedback, and a temptation to guess ahead at abstractions instead of letting duplication drive them.

3. The refactor step removes duplication, including duplication between the test and the code, and improves the design without changing behavior, running the tests after each small change. It needs no new failing test because it adds no new behavior. Only new behavior needs a new red test, and the existing green tests are the safety net that shows behavior hasn't changed. After a long run of red-green with no refactoring you'd have fast-written, messy code full of the "sins" from green: hard-coded values, copy-paste and ugly conditionals that never got generalized or cleaned up. (The explainer lists Fowler's bliki as a source but doesn't quote that specific claim; this answer rests on what it says about refactoring.)

4. Beck explicitly says writing all the tests up front is not TDD; "Canon TDD" restates the workflow as one test at a time. Up front you write a test list on paper, a to-do list of scenarios you think the code needs to handle. During the loop you turn exactly one item into a concrete runnable test, add new ideas, edge cases and refactorings to the list instead of acting on them, cross items off as they go green, and stop when the list is empty. He advises against making them all runnable at once because you'd lose the design feedback each test gives you, and you'd have to rework a pile of tests when the first one teaches you something.

5. You choose based on how confident you are. Use Fake It (return a constant, then replace it with variables) when you're unsure how to implement something or want the smallest step. Use Triangulate when you can't yet see the right abstraction and need two or more examples to force it. Use Obvious Implementation when the solution is clear, and drop back to smaller steps if you get a surprise red. This shows that "tiny steps" is a misconception: step size is a dial, like shifting gears or a well-pump bucket, and the tests let you go small when uncertain and faster when confident.

6. Writing the test first makes you the first client of your own code. It forces interface decisions: what the call looks like, what it's named, what it takes and what it returns. How the code works, the implementation design, is left for the green and refactor steps. The split is useful because you design the interface before you're tangled up in the internals, and code that's awkward to test, which usually means it's awkwardly coupled, shows up immediately while it's still cheap to change.

7. Tests that mock most collaborators are coupled to implementation details, so refactoring, which changes structure without changing behavior, breaks them. That destroys the safety net the refactor step depends on, makes refactoring costly, and works against the whole loop, a central theme of the 2014 "Is TDD Dead?" conversations. Pasting the code's own computed output into expected values is a mistake Beck names directly: it defeats the double-check the test is meant to give, because the test can't fail when the code is wrong. Their tests should check behavior at whatever level gives useful feedback, and their expected values should be worked out independently, ideally before the code exists, so that each test can genuinely fail (seen red first) and survives refactoring.

8. Beck would say TDD is mainly a design and development discipline, not a testing technique. Its purpose is "clean code that works", reached by splitting "works" (red to green) from "clean" (refactor), and it's a way of managing fear and controlling the gap between decision and feedback. The test suite and executable documentation are valuable byproducts, not the goal. On how much to use it, he says "I get paid for code that works, not for tests, so my philosophy is to test as little as possible to reach a given level of confidence": the rule is that new behavior is driven by a failing test, not a coverage target, and he adjusts step size and test effort to his confidence.
