1. A move changes nothing at runtime. It is the same shallow memcpy, and what changes is the compiler's bookkeeping: the source is marked as moved-from and statically dead, so only the destination will ever drop the resource. With a `Copy` type the source stays valid, so after the copy two values hold the same bits. If those bits owned a resource that `Drop` frees (like a `String`'s heap buffer), both copies would free it at scope end, which is a double free. That is why a type can't be both `Copy` and have a custom `Drop`.

2. The classic case is `let first = &v[0]; v.push(4); println!("{first}");`. `push` may reallocate the vector's buffer, which leaves `first` pointing into freed memory, so reading it is a use-after-free. Iterating with `for x in &v` and pushing inside the loop has the same problem. The rule prevents iterator invalidation and dangling references, which are memory-safety bugs that happen even with one thread, not just data races.

3. Under NLL a borrow is live only from where it's created to its last use, not until the closing `}`. If `r` is never used after `push`, the shared borrow has already ended when `push` asks for `&mut v`, so nothing conflicts. (not covered) The explainer doesn't discuss this exact case, but it does say that when an owner leaves scope its drop runs. My reasoning is that if `r` sat inside a struct with a custom `Drop`, that drop at end of scope would count as a use of the borrow, so the borrow would stay live across `push` and you'd get E0502.

4. `'a` is a region chosen at each call site during which both `x` and `y` are valid. In practice it's the overlap of the two borrows, meaning the shorter one, and the result is only guaranteed valid for that region. Rust requires the annotation because the checker reasons locally: at a function boundary it looks only at signatures, never at bodies. The signature is a contract that tells callers which input the output borrows from. The compiler doesn't evaluate the `if` to see which branch is taken, so it assumes the worst case.

5. Yes. `T: 'static` does not mean "T lives forever." It means T contains no borrows shorter than `'static`, so it could be kept around indefinitely if you wanted, and an owned `String` built at runtime qualifies even though it gets dropped normally. `&'static T` is a reference that must point to data valid for the whole program run, such as a string literal stored in the binary. A runtime `String` could not give you that without, for example, leaking it.

6. If `&mut T` were covariant, you could treat a `&mut &'long str` as a `&mut &'short str`. Here's the sketch: take `let mut s: &'static str = "hi";` and a function `fn put<'b>(slot: &mut &'b str, x: &'b str) { *slot = x; }`. Call `put(&mut s, &local_string)` inside an inner block, then let `local_string` drop and print `s` afterward. Through the shortened view you've written a short-lived `&str` into a slot the caller believes holds a long-lived one, which leaves a dangling reference. Invariance forbids that substitution, and shared `&T` can stay covariant because you can't write through it.

7. Interior mutability (`Cell`, `RefCell`, and `Mutex`/`RwLock`/atomics for threads) doesn't break aliasing XOR mutation. It moves the check from compile time to runtime. What you give up is the static guarantee: `RefCell::borrow_mut` panics if a borrow is already active (and `Mutex` blocks), so a conflict becomes a runtime failure instead of a compile error. You also pay some runtime cost and add complexity, which is why the explainer puts these near the end of the toolkit, after cheaper fixes. (The explainer doesn't explain how `Cell` differs from `RefCell` in detail.)

8. When you access fields directly, the checker sees `self.x` and `self.y` as separate places and allows two disjoint `&mut` borrows. A method like `x_mut(&mut self)` has a signature that borrows all of `self` uniquely, and the checker reasons locally from signatures, never from bodies. So it has to assume `x_mut` might touch everything, and the second call gives E0499. The principle is that signatures are contracts. Fixes include accessing the fields directly or adding a method that returns both at once, like `fn split(&mut self) -> (&mut X, &mut Y)`.
