# Rust quiz answers (learner Y)

1. A move changes what the compiler lets you do with the source, not the bytes. After `let y = x;` for a non-`Copy` type, `x` is statically dead: using it is E0382, and no destructor runs for it (or a hidden drop flag records that it moved). Without that rule, both `x` and `y` would free the same buffer and you would get a double free. My reasoning on the second part: a `Copy` type leaves both values usable and both would run `Drop`, which is the same double free, so the two can't go together. The explainer does not state that last rule directly. (partly not covered)

2. Take `let first = &v[0]; v.push(4);` and then read `first`. The push may reallocate the vector's buffer, which leaves `first` pointing at freed memory: a dangling reference, use-after-free. This is the iterator-invalidation case Walton used to justify the rule "you may not modify an object while a pointer to it exists, except through that pointer." So the rule is about memory safety in a single thread, and race freedom comes as a bonus.

3. Under NLL a reference's lifetime is the set of control-flow points where it may still be used, not the whole lexical block. If `r` is never used after `let r = &v[0];`, the borrow is already over when `v.push(1)` runs, so there is no conflict. My reasoning on the second part: if `r` is stored in a struct with a `Drop` impl, the destructor runs at the end of scope and could look at the reference, so that drop counts as a later use and keeps the borrow alive across the push. The explainer doesn't spell out how drops count as uses. (partly not covered)

4. `'a` is not a fixed duration and it doesn't set how long anything lives. It names the region where the data lives, and it is shared by both inputs and the output, so it means "the result points into the same region as the inputs." When the two inputs live for different lengths of time, outlives subtyping lets the longer one stand in for the shorter, so `'a` is effectively the shorter (overlapping) region and the result can't outlive it. Rust requires it in the signature because, like Cyclone, it never infers lifetimes in prototypes: signatures are the contract, so callers and separately compiled code can rely on them, and full inference (as in the ML Kit) made lifetimes change unpredictably when the program changed. Also, with two reference inputs the elision rules can't tell which one the result borrows from, so the compiler won't guess.

6. The explainer only says that a longer-lived reference can stand in for a shorter-lived one (outlives subtyping); it does not cover variance. My reasoning: if `&mut T` were covariant, you could treat `&mut &'long str` as `&mut &'short str`, write a short-lived reference through it, and then read it back through the original as `&'long str` after the short-lived data is gone, giving a dangling reference. With a shared `&` you can only read, so substituting a longer lifetime is safe, but `&mut` allows writes, so the type has to match exactly. (not covered)

7. In Rust `&` really means "shared," not "read-only," and `&mut` means "unique." The rule is that aliasing and mutation must never happen together unchecked. `Cell`/`RefCell` (and `Mutex` across threads) allow mutation through a shared reference by checking it some other way: `RefCell` enforces many-readers-or-one-writer at runtime instead of at compile time. What you give up is the static guarantee: a violation becomes a runtime failure instead of a compile error, there is checking overhead, and you lose the no-aliasing optimizations the compiler gets from `&mut`.

8. `&mut self.x` and `&mut self.y` borrow two separate places, so the checker can see they don't overlap. A getter that takes `&mut self` borrows all of `self` uniquely for as long as the returned reference lives, because the checker only looks at the function's signature, not its body. That follows the principle the explainer describes from Cyclone and Rust: signatures are explicit and inference happens only inside bodies, so callers rely on the stated contract and don't depend on implementation details. The explainer doesn't discuss field-level borrows or this exact case, so this is my reasoning from that principle. (partly not covered)
