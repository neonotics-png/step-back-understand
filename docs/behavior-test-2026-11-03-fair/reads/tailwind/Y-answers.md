# Tailwind quiz answers (learner Y)

1. If the CSS depends on the HTML (semantic classes like `.author-bio`), you can restyle the HTML from the stylesheet, but you cannot reuse the CSS. If the HTML depends on the CSS (utilities), you can reuse the CSS, but you cannot restyle the HTML from the stylesheet. You have to edit the markup. Wathan chose reuse. Under this framing, Tailwind fits poorly in a project with no component or partial system that holds each class list once, because there the long class lists get repeated everywhere. It also follows that Tailwind is a poor fit when you need to restyle markup from the stylesheet alone. That second point is my inference from the framing.

2. Utilities can express hover, focus and media queries through variant prefixes such as `hover:bg-sky-700` and `sm:grid-cols-3`, and inline styles cannot. Utilities also draw their values from a predefined design system, while inline styles let every value be a magic number. Two parts of the critique still hold. First, the markup really is bloated and looks like inline styles, and Builder.io's round-up concedes this. Second, arbitrary values like `p-[5px]` bypass the scales, so "no magic numbers" is only a default, not a guarantee.

3. Inside `@theme`, `--color-brand-500` becomes a normal CSS variable on `:root`, and because it sits in the `--color-*` namespace it also creates utilities: `bg-brand-500`, `text-brand-500`, `fill-brand-500`. If you declare it under `:root` instead, you get only the CSS variable and no utilities. The docs say to use `:root` for variables that should not map to a utility class. Having tokens as real CSS variables at run time, not v3's build-time JavaScript values, means other CSS and code can read them while the page runs. My inference is that this also lets you redefine them at run time, for example for theming. The explainer doesn't spell that out.

4. (Partly not covered.) The explainer says that since the JIT engine, Tailwind generates CSS only for the classes you actually use. So the reasonable conclusion is that it looks for complete class names like `bg-red-500` in your source, and a string assembled at run time from `bg-${color}-500` never shows up as a complete class it can find. My best reasoning is that the fix is to write out the complete class names, for example a lookup from each color to its full `bg-…-500` string. The explainer does not describe how detection works or give this fix. The same "generate only what's used" rule explains why "your CSS stops growing": the CSS covers only the set of classes in use, not every possible value.

5. The v4 docs on duplication point to loops, framework components and template partials. Write the button once as a component or partial, and the 12-class list lives in one place. The v3 docs warn "don't use `@apply` just to make things look 'cleaner'". Doing that brings back the costs utilities were meant to remove: you have to name things again, switch files, take on global side effects, and ship a bigger bundle. Using `@apply` everywhere gives you semantic CSS back, with both camps' downsides together.

6. (Mostly not covered.) The explainer only says that class order in the markup does not decide which rule wins ("The markup lies to you"). My reasoning is that the generated stylesheet's own rule order decides it, not the attribute order, so `grid` wins wherever its rule appears later or carries more weight in the CSS. In a `<Button className=...>` component, a caller who passes an override like a different padding can't count on it beating the component's built-in class just by appending it. The explainer does not say how teams handle this.

7. The criticism is true when colors are hard-coded, scattered class by class, and no component holds each pattern once. It is also true when arbitrary values like `bg-[#...]` were used, because those bypass the theme. It is false for value-level changes made through the theme: redefine the `--color-*` variables in `@theme` (or give `blue` new values), and every utility built on them changes. My inference is that this holds best when classes name a semantic token like `brand-500` rather than `blue-500`. Pattern-level changes, such as how every button looks, are handled by components, partials and loops that hold each class list once, not by the theme.

8. (Not covered.) The explainer doesn't discuss tooling or the upgrade process. It does say v4 moved the config from `tailwind.config.js` into CSS `@theme` blocks, turned tokens from build-time JS into run-time CSS variables, and changed spacing from a fixed list to `--spacing` multiplied by a number. My reasoning: styles are plain strings scattered through the markup, and nothing checks them the way a type checker would. So when a version changes what classes or config mean, as with the v3-to-v4 move from the JS config to `@theme`, every class string and config entry has to be found and changed by search or a codemod, not by following compiler errors.
