# Tailwind quiz answers (X)

1. (not covered) The explainer cites Wathan's 2017 essay and gives its gist, "the separation that matters is by component, not by language," but never explains "dependency direction" or its two directions. My best reasoning: in one direction the CSS is written first and the markup depends on its class names, so styles can be reused but the HTML has to fit them. In the other, the HTML is written first and the CSS depends on the markup's structure, so the markup stays clean but the CSS is tied to it and hard to reuse. Tailwind is a poor fit for document-centric projects (content sites, CMS markup, heavily themed or user-skinned pages, plain HTML without templating), where clean semantic HTML that can be restyled separately matters most.

2. Inline styles accept any value, while utilities limit you to a token scale, which keeps spacing, color and type consistent. Inline styles also can't handle `:hover`, focus, media queries or dark mode, but utilities can through variant prefixes. The build step also turns each utility into one shared rule, so CSS stays small and finite. What still holds is that styling now lives in the markup, so you get long "class soup" strings that are hard to scan and review, and the markup's structure gets buried. Some people simply never get past how that looks.

3. Inside `@theme`, the `--color-*` namespace tells Tailwind to generate utilities from the token: `bg-brand-500`, `text-brand-500`, `border-brand-500`, `fill-brand-500` and so on. Tailwind also emits the variable on `:root`. Declaring it only under `:root` gives you a plain CSS variable and no utility classes. That is why the theming pattern defines raw variables in `:root`/`.dark` and maps them through `@theme`. Because tokens are real runtime custom properties (in v3 they existed only at build time), you can use `var(--color-brand-500)` in normal CSS, inline styles, canvas or JS. Semantic tokens can also point at variables you swap per theme, so `bg-surface text-fg` restyles itself without `dark:` on every element.

4. Tailwind is a compiler that scans source files for complete class-name strings and generates CSS only for the ones it finds. It never runs your code, so it never sees `bg-blue-500` built by interpolation, and no rule exists for it. (`bg-red-500` only works because it appears in full somewhere else.) The idiomatic fix is to write the full class names out, for example in a lookup map such as `{ red: "bg-red-500", blue: "bg-blue-500" }`, and pick from it. This shows that output depends on which literal class names appear in the source, not on the pages you render. Each utility becomes one shared rule however many times it is used, so the CSS grows with your design-system vocabulary and stops growing once that vocabulary is in use.

5. The recommended unit of reuse is the component: put the class string once in a `Button` (React/Vue/Svelte, a Blade partial and so on) and use that component in all 30 places, using `clsx`/`cva` for variants such as size or intent. `@apply` is meant for places you can't add classes to, like markdown output or third-party widgets. The docs warn against using it to rebuild BEM-style component classes because that brings back the naming problem (and the separate stylesheet) that Tailwind exists to remove. If the project is plain static HTML with no templating, the repetition is a real cost, and that is where Tailwind fits worst.

6. When two utilities set the same property, the winner depends on where their rules sit in the generated stylesheet, not on their order in the class attribute. Here the `grid` rule comes later in Tailwind's output, so it wins. With a reusable `<Button className=...>`, the component's built-in `p-2` and a caller's `p-4` both land on the element, and the caller can't rely on their class winning. Teams usually fix this with `tailwind-merge`, which resolves conflicts so the last class wins (`p-2 p-4` gives `p-4`), often together with `cva` variants. The explainer notes that needing this tool is itself a sign of friction.

7. It's true when the codebase uses raw palette classes (`bg-blue-600`) or arbitrary values (`bg-[#1da1f2]`) everywhere instead of its own tokens, because then every class list names the old color. It's false when the team defined brand or semantic tokens in `@theme` (`--color-brand-500`, `--color-surface`): changing the token updates every use at once, which is the point of the token layer. Value-level changes (colors, fonts, spacing, radii) go through theme tokens. Pattern-level changes (how a button or card is put together) go through components and their variants, where the class string is written once.

8. Styles are plain strings, so nothing type-checks them. A wrong or renamed class fails silently, and an editor plugin, a Prettier plugin and the scanner all have to understand Tailwind's vocabulary separately. Plain CSS has standard tooling, and typed token-driven systems (Panda, vanilla-extract, StyleX) can catch errors at compile time. In the v3-to-v4 upgrade, `shadow-sm` became `shadow-xs` and the `ring` defaults changed. Those names are spread through markup, including dynamically built or lookup-map strings, so you need a codemod (`npx @tailwindcss/upgrade`) or a careful search-and-replace instead of a compiler pointing out each broken use. The config also moved from `tailwind.config.js` to CSS `@theme`, and plugin APIs changed, which adds to the migration churn.
