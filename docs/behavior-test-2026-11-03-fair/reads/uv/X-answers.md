# uv quiz answers

1. Rust alone doesn't explain it. Most of the speed comes from the design. uv keeps one global cache of already-unzipped wheels, so a warm install mostly creates links (clone or hardlink) rather than downloading, unzipping and copying. Resolution uses PubGrub, a solver based on conflict-driven clause learning, and one shared engine runs both front ends. Astral's own figures are 8-10x faster than pip with no cache and 80-115x with a warm cache, which points at caching and linking more than at the language. How uv learns a package's dependencies without downloading the whole wheel is (not covered). My best guess is that it reads only the wheel's metadata, from the index or from part of the file, instead of fetching everything.

2. The cache stores each wheel once, unzipped into a plain directory (the `Archive` bucket, plus content-addressed `Files` hardlinked into it). An install then links files from the cache into the venv: `clone` (copy-on-write) by default on macOS and Linux, `hardlink` on Windows. That takes milliseconds and almost no new disk space. If the cache and the venv are on different filesystems, uv can't link and falls back to slower copying, so put `UV_CACHE_DIR` on the same volume as the venv. Why `symlink` is discouraged is (not covered). My reasoning: a symlinked venv still points into the cache, so cleaning or replacing cache entries (they can be "atomically replaced and removed") would break the environment, while clones and hardlinks keep their own reference to the data.

3. uv is a single static binary with "no direct Python dependency", so you can install it separately from Python itself. It doesn't depend on whichever interpreter or environment happens to be on the machine, and a tool that doesn't need Python can install Python. pip runs inside an interpreter, so you need a working Python before pip can do anything. When there is no Python, or the version is wrong, uv downloads a python-build-standalone build. These are portable builds you can "download, unzip, and run", and Astral now maintains them. (The exact command and how a version gets selected are not covered.)

4. `uv pip compile` follows pip-tools: it writes a platform-specific `requirements.txt` for the current environment unless you pass `--universal`. `uv lock` writes a uv-specific, committed `uv.lock` that is always universal and covers Linux, macOS and Windows and all supported Python versions at once. A package can appear twice because the forking resolver splits the resolution wherever requirements differ by environment marker (for example `python_version < "3.11"`) and saves each branch as `resolution-markers`, so different forks can pin different versions. The `requires-python = ">=3.8"` failure follows from that universal goal, though the explainer doesn't spell this case out (partly not covered). The lock has to work for every Python the project claims to support, including 3.8 and 3.9, so a dependency that needs 3.10 or later can't be satisfied there, whatever you run locally. Raising `requires-python` to ">=3.10" would fix it.

5. (not covered) The explainer doesn't describe these flags. My best guess from the names: `--locked` checks that `uv.lock` still matches `pyproject.toml` and errors instead of re-locking, which suits CI, where a stale lockfile should fail the build. `--frozen` installs from `uv.lock` as it stands without checking it against `pyproject.toml`, which suits an early Docker layer where only the lockfile has been copied in. A new release on PyPI should not make `uv.lock` outdated, because the lockfile records exact resolved versions and is meant to stay stable. "Outdated" most likely means out of step with `pyproject.toml`, not behind the index.

6. These are two front ends from different eras. `uv pip` is the pip/pip-tools layer, which changes the environment directly. The project interface (Cargo-style) treats `pyproject.toml` plus `uv.lock` as the source of truth and makes the `.venv` match them. `uv sync`, like `pip-sync`, installs and uninstalls whatever it takes to match the lock, so `rich` (not in the lock) gets removed, and `uv run` re-locks and re-syncs every time anyway. The developer should have declared `rich` as a dependency in `pyproject.toml` through the project interface, so it gets locked and synced. The exact command (probably something like `uv add`) is not covered by the explainer.

7. uv by default "prefers the first index that has a package", which the explainer describes as a defence against dependency confusion. If `acme-utils` exists on the private index (searched first), uv takes it from there and never looks at the attacker's 99.0 on PyPI. pip's behaviour is (not covered) in detail, but the contrast implies that pip with `--extra-index-url` treats all indexes as one pool and picks the highest version, so it would install the attacker's 99.0. The setting that changes uv's default is also (not covered). It's presumably an index-strategy option that lets uv consider every index, or pick the best version across them.

8. The likely cause: uv "skips `.pyc` compilation by default", so no bytecode gets written at install time. The first imports after the container starts have to compile the modules then, which slows the first request. uv chose this default to make installs faster: compiling every module would cost time on each install, and uv puts install speed first. The fix is to compile bytecode at image build time, using uv's compile-bytecode option on install (the exact flag name is not covered) or by running a compile step in the Dockerfile, so the cost is paid once in the build and not on every container start.
