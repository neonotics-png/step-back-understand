# uv quiz answers

1. Rust helps, but most of the speed comes from design. uv runs downloads, unpacking, metadata fetching and installs in parallel where pip mostly works serially. It uses a PubGrub-based resolver that backtracks efficiently. Installs mostly link files from the global cache instead of copying them, and by default it skips work like `.pyc` compilation and seeding pip/setuptools into new venvs. To learn a package's dependencies it only needs the metadata. It uses PEP 658/714 metadata files when the index provides them, and otherwise sends HTTP range requests that read just the zip central directory and the `METADATA` file from the remote wheel.

2. Each wheel is unpacked once into the global content-addressed cache. Installing into a venv then just creates entries in `site-packages` that point at those cached files, using `clone` (copy-on-write reflink, the default on macOS/Linux) or `hardlink` (the default on Windows). Both are near-instant and use almost no extra space. If the cache and venv are on different filesystems (a Docker bind mount, a separate `/workspace` volume, an external disk), linking fails. uv then warns and falls back to a full copy, which works but is slower. The fix is to put the cache on the same volume with `UV_CACHE_DIR`, or to set `UV_LINK_MODE=copy` when copying is intended. `symlink` is discouraged because the venv depends on the cache files, so `uv cache clean` breaks every environment.

3. pip lives inside a Python install, so a broken Python means a broken installer, and each interpreter carries its own pip. uv is self-contained native code (statically linked with musl on Linux), so it starts in milliseconds and works no matter what state the machine's Pythons are in. You can install it with curl, brew, pipx/pip or by copying it into a Docker image. When no suitable interpreter exists, uv downloads a managed CPython build from Astral's python-build-standalone (it also offers PyPy and GraalPy). By default it does this automatically (`python-downloads = "automatic"`), prefers managed Pythons over system ones, and respects the version pinned in `.python-version` (`uv python pin`).

4. `uv pip compile` produces a `requirements.txt` resolved for the one machine and Python that ran it, unless you pass `--universal`. `uv lock` produces a universal, hashed `uv.lock` that covers every OS, architecture and Python version allowed by `requires-python`. When dependencies differ by environment marker, the resolver forks and solves each region separately, so the same package can appear twice at different versions, each guarded by markers (the regions are listed in `resolution-markers`). Because the lock must cover the whole `requires-python` range, `>=3.8` means uv also has to find a valid solution for 3.8 and 3.9. A dependency that only supports 3.10+ makes those regions unsolvable, even if you only run 3.12. The fix that follows from this is to raise `requires-python` to `>=3.10`, or to put a Python-version marker on that dependency. (The explainer implies this failure mode rather than spelling it out.)

5. `--locked` makes uv error if `uv.lock` is out of date with `pyproject.toml`. Use it in CI to catch a lock someone forgot to update or commit, or in a Docker build to fail when `pyproject.toml` changed without a re-lock. `--frozen` uses the lock as-is without checking whether it is fresh. Use it in Docker builds and deploys where `pyproject.toml` may not be present. (The explainer's own Docker example uses `--locked` in its early dependency layer, with both files bind-mounted.) A new release on PyPI never makes an existing lock outdated. "Outdated" means only that the lock no longer matches `pyproject.toml`'s input requirements, and upgrades happen only when you run `uv lock --upgrade` or `--upgrade-package` explicitly.

6. In the project interface, `pyproject.toml` and `uv.lock` own the environment's state. `uv sync` makes `.venv` match the lock exactly and removes anything not in it, and `uv run` syncs too. `rich` was installed imperatively with `uv pip`, so the lock never knew about it and the next sync removed it. The `uv pip` interface is pip-like and imperative: you own the environment and mutate it directly, with no lockfile or `pyproject.toml` management, though it shares the same resolver, cache and linker. The developer should have run `uv add rich` to keep it, or `uv run --with rich ...` for a one-off trial.

7. pip merges all configured indexes and picks the best version, so it would choose the attacker's `acme-utils` 99.0 from PyPI. This is a "dependency confusion" attack. uv's default `first-index` strategy takes a package's versions only from the first index that has it, so `acme-utils` comes only from the private index and PyPI's 99.0 is never considered. uv does this deliberately to block that attack. `--index-strategy unsafe-best-match` restores pip's merge-and-pick-best behaviour. (In the project interface you can also pin a package to a named index with `[tool.uv.sources]`.)

8. The most likely cause is that uv skips bytecode compilation at install time. The `.pyc` files are generated on first import, so the first request pays that cost. uv chose this default to do less work at install time, which is part of why installs are fast. In Docker images, enable compilation at build time with `--compile-bytecode` or `UV_COMPILE_BYTECODE=1`. The cost then moves into the image build instead of the first request.
